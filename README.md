# ระบบติดตามรายได้แปลงเกษตรทฤษฎีใหม่ — Dashboard (React + Vite)

ตอนนี้มีครบ 4 หน้าหลัก เชื่อมต่อกับ Apps Script ที่ deploy ไว้แล้ว (ดู `Code.gs`, `ReadApi.gs`,
`EntryApi.gs`, `ApprovalApi.gs` ที่ส่งให้ก่อนหน้านี้):
- **ภาพรวม (สาธารณะ)** — สรุปทั้งโครงการ กรองตามปี/เดือน/จังหวัด/ชุมชน
- **รายชุมชน (ภายใน)** — ดูรายละเอียดของชุมชนเดียว แบ่งเป็น 4 แท็บ: ภาพรวม,
  วิเคราะห์เชิงลึก, เปรียบเทียบ, รายสมาชิก
- **กรอกข้อมูล** — ตัวแทนพื้นที่กรอกข้อมูลรายเดือนของชุมชนที่รับผิดชอบ (ล็อกเดือนที่
  มีข้อมูลรออนุมัติอยู่แล้ว, เตือนช่องที่เปลี่ยนจากเดือนก่อนเกิน 300%, เพิ่มสมาชิกใหม่ได้)
- **ตรวจสอบ/อนุมัติ** — ทีมกลางตรวจสอบข้อมูลที่ส่งเข้ามา เทียบกับเดือนก่อน แล้วอนุมัติ/ตีกลับ

## วิธีรันครั้งแรก

```bash
npm install
npm run dev
```

จะเปิดที่ `http://localhost:5173` (หรือพอร์ตอื่นถ้าพอร์ตนี้ถูกใช้แล้ว)

## ⚠️ ต้องตั้งค่าก่อนใช้งานจริง

เปิดไฟล์ `src/api/appsScript.js` แล้วแก้บรรทัดนี้:

```js
const APPS_SCRIPT_URL = 'https://script.google.com/macros/s/YOUR_DEPLOYMENT_ID_HERE/exec';
```

แทนที่ด้วย URL จริงที่ได้จาก Apps Script > Deploy > New deployment > Web app
(URL ที่ลงท้ายด้วย `/exec`)

ถ้าไม่แก้ตรงนี้ หน้าเว็บจะค้างที่ "กำลังโหลดข้อมูล..." แล้วแสดง error

หน้า "กรอกข้อมูล" และ "ตรวจสอบ/อนุมัติ" ต้องใส่รหัสผ่านร่วมของระบบด้วย (ตั้งไว้ฝั่ง
Apps Script ผ่าน `setEntryPassword()` ใน `Auth.gs`) — ไม่มีรหัสผ่านฝังอยู่ในโค้ด React เลย

## หมายเหตุสำคัญเรื่องแท็บ "ภาพรวม" ในหน้ารายชุมชน

mockup เดิมมีแผง "สถานะคุณภาพข้อมูล" ที่อธิบายปัญหาเฉพาะของไฟล์ Excel ต้นฉบับ
(เช่น ชีตสรุปจังหวัดคำนวณผิด) — ข้อมูลแบบนี้ไม่สามารถคำนวณซ้ำได้จากข้อมูลใน Google
Sheets ที่ deploy จริง (มีแค่ communities/monthly_records/monthly_summary ไม่มีร่องรอย
ไฟล์ Excel ต้นฉบับ) จึงแทนที่ด้วยแผง **"ความครบถ้วนของข้อมูล"** ซึ่งคำนวณได้จริงจาก
ข้อมูลที่มี (เทียบจำนวนเดือนที่มีข้อมูลกับ 12 เดือนที่ควรมีต่อปีงบ)

## หมายเหตุเรื่องหน้า "ตรวจสอบ/อนุมัติ"

mockup เดิมมีสถิติ "อนุมัติแล้ว/ตีกลับใน 7 วันล่าสุด" แต่ backend ปัจจุบัน
(`getPendingSubmissionsForReview()`) อ่านได้แค่รายการที่ status=pending เท่านั้น จึงยังไม่มี
ทางคำนวณสถิติย้อนหลังได้ — หน้าจอจะมีหมายเหตุอธิบายเรื่องนี้ไว้ ถ้าต้องการฟีเจอร์นี้จริง
ต้องเพิ่ม endpoint ใหม่ฝั่ง Apps Script ที่อ่านได้ทุก status

## โครงสร้างไฟล์ที่สำคัญ

```
src/
  api/appsScript.js              — ฟังก์ชันเรียก Apps Script ทั้งหมด (อ่าน/เขียน/อนุมัติ)
  styles/tokens.css              — สีและฟอนต์ทั้งระบบ
  pages/fiscalYears.js           — ค่าคงที่/ฟังก์ชันเกี่ยวกับปีงบ ใช้ร่วมหลายหน้า
  pages/Homepage.jsx + homepageAggregations.js       — หน้าภาพรวม
  pages/CommunityView.jsx + communityAggregations.js — หน้ารายชุมชน (ภายใน)
  pages/communityTabs/                                — 4 แท็บย่อยของหน้ารายชุมชน
  pages/EntryForm.jsx + entryFormHelpers.js           — หน้ากรอกข้อมูล
  pages/ApprovalQueue.jsx + approvalQueueHelpers.js   — หน้าตรวจสอบ/อนุมัติ
  components/                    — ส่วนที่ใช้ร่วมกัน (TopBar, FilterBar, SubTabs, ...)
```

## ฟีเจอร์ใหม่: ตรวจจับปัญหาข้อมูลอัตโนมัติ + แจ้งเตือนชุมชนยังไม่ส่งข้อมูล

**หน้า "คุณภาพข้อมูล" (ใหม่)** — รันการตรวจสอบ 3 อย่างทั่วทั้งระบบทุกครั้งที่เปิดหน้า ไม่ต้อง
รอให้สแกนมือทีหลังอีก: ชื่อสมาชิกที่อาจซ้ำกัน, ข้อมูลที่อาจคัดลอกข้ามปี, ช่วงที่อาจไม่ได้
กรอกข้อมูลจริง — เป็นเวอร์ชัน JS ของสคริปต์ Python ที่ใช้สร้าง near_duplicate_names.csv,
suspected_carryover_duplicates.csv, likely_unentered_month_runs.csv ก่อนหน้านี้ ตัวเลขอาจ
ไม่ตรงเป๊ะกับ CSV เดิมเล็กน้อย (การตรวจชื่อซ้ำใช้ Levenshtein distance แทน Python's
difflib.SequenceMatcher เพราะไม่มี library คล้ายกันใน JS — เป็นวิธีคำนวณคนละแบบ แม่นยำ
ใกล้เคียงกันแต่ไม่ใช่อัลกอริทึมเดียวกัน) ไฟล์อยู่ที่ `src/pages/dataQualityChecks.js`
หน้านี้ต้องโหลด monthly_records ทั้งหมด (~59,000 แถว ไม่กรองตามชุมชน) จึงอาจใช้เวลาโหลด
สักครู่ (ทดสอบแล้วประมาณ 3-4 วินาที)

**หน้าแรก: ส่วน "ชุมชนที่ยังไม่ส่งข้อมูลเดือนนี้" (ใหม่)** — แสดงชุมชนที่ยังไม่มีข้อมูลของ
เดือนปฏิทินปัจจุบันจริง (ไม่ใช่ตัวกรองด้านบน) พร้อมคาดการณ์รายได้จากค่าเฉลี่ยเดือนเดียวกัน
ของปีก่อน ๆ ที่มีข้อมูลจริง (seasonal-naive forecast — ไม่รวมเดือนที่ถูกตัดออกเพราะ 0
ต่อเนื่องนาน ไม่งั้นค่าเฉลี่ยจะต่ำเกินจริง) ฟังก์ชัน `buildOverdueReport()` อยู่ใน
`src/pages/homepageAggregations.js`

**ป้องกันชื่อซ้ำเพิ่มในหน้ากรอกข้อมูล (ใหม่)** — ตอนกด "เพิ่มสมาชิกใหม่" ถ้าชื่อที่พิมพ์คล้าย
กับชื่อที่มีอยู่แล้วในชุมชนนั้น จะมีข้อความเตือนให้ตรวจสอบก่อนส่ง (ไม่ได้บล็อกการส่ง เผื่อ
เป็นคนละคนจริงที่ชื่อคล้ายกันโดยบังเอิญ) แก้ปัญหาที่ต้นเหตุไม่ได้ (ข้อมูลเก่าที่ซ้ำอยู่แล้วต้อง
แก้ที่ Sheets โดยตรง — ดูหน้า "คุณภาพข้อมูล") แต่ช่วยไม่ให้เกิดซ้ำใหม่เพิ่มจากการพิมพ์ผิด

## ฟีเจอร์ใหม่: ตัวกรอง "ภาค"

เพิ่มในทั้ง 3 จุดที่มีตัวเลือกพื้นที่:
1. **หน้าแรก (FilterBar)** — เลือกภาคแล้วจังหวัด/ชุมชนจะกรองเหลือแค่ในภาคนั้น (กดเลือก
   จังหวัดจากกริดด้านล่างก็จะปรับภาคให้ตรงกันอัตโนมัติด้วย) ตัวเลข "ชุมชนที่มีข้อมูล X/Y"
   ตอนนี้ Y จะเปลี่ยนตามขอบเขตที่กรองไว้ (เช่น กรองภาคแล้วเหลือ 36 ชุมชน จะโชว์ X/36 ไม่ใช่
   X/85 เหมือนเดิม ซึ่งดูเข้าใจผิดว่าชุมชนส่วนใหญ่ไม่มีข้อมูลทั้งที่จริงแค่ไม่ได้อยู่ในภาคนั้น)
2. **หน้าข้อมูลเชิงวิเคราะห์ (ตัวเลือกชุมชนหลัก)** — เลือกภาคเพื่อย่อรายชื่อ dropdown ชุมชน
   ให้สั้นลง ถ้าชุมชนที่กำลังดูอยู่ไม่อยู่ในภาคใหม่ จะสลับไปชุมชนแรกของภาคนั้นให้อัตโนมัติ
3. **กล่องดาวน์โหลดข้อมูลรายชุมชน** — มีตัวกรองภาคของตัวเอง แยกอิสระจากข้อ 2 (ไม่ใช้ตัวกรอง
   เดียวกัน) ตามหลักการเดิมที่กล่องนี้ไม่ผูกกับตัวเลือกที่กำลังดูอยู่บนหน้าจอหลัก

ตัวกรองภาคเป็นตัวช่วยย่อรายชื่อ ไม่กระทบปุ่มดาวน์โหลดที่ตกลงกันไว้แล้วว่า "ดาวน์โหลดทั้งระบบ
เสมอ ไม่สนใจตัวกรอง" (ปุ่มดาวน์โหลดของหน้าแรกยังคงดาวน์โหลดทั้ง 85 ชุมชนเหมือนเดิม)

## ฟีเจอร์ใหม่: ปุ่มดาวน์โหลดข้อมูล (4 จุด)

**1. หน้าแรก** — ปุ่ม "ดาวน์โหลดข้อมูล" ใต้ตัวกรอง ดาวน์โหลด Excel (.xlsx) 3 ชีต
(สรุปรายเดือน, สรุปรายจังหวัด, สรุปรายชุมชน) ของ**ทั้งระบบเสมอ** ตามปีที่เลือกไว้บนตัวกรอง
— ไม่สนใจว่ากำลังกรองจังหวัด/ชุมชนอะไรอยู่บนหน้าจอ (ตามที่ตกลงกันไว้)

**2. หน้าข้อมูลเชิงวิเคราะห์** — ปุ่ม "ดาวน์โหลดข้อมูลรายชุมชน" เปิดกล่องเลือกแยกอิสระ
(เลือกชุมชน + ปีงบได้หลายปีหรือทุกปี โดยไม่กระทบสิ่งที่กำลังดูอยู่บนหน้าจอหลัก) ดาวน์โหลด
Excel 3 ชีต (สรุปรายเดือน, รายสมาชิก, สรุปการวิเคราะห์)

**3. หน้าใหม่ "รายงานผู้บริหาร"** — ดาวน์โหลด PDF 1 หน้า (KPI รวม, กราฟแนวโน้มรายเดือน,
Top 5 รายได้สูงสุด/เติบโตเร็วสุด) พร้อมนำเสนอ ไม่ต้องเปิด Excel เอง

**4. ปุ่ม "เปรียบเทียบทั้งภาค/จังหวัด"** อยู่ในหน้า "รายงานผู้บริหาร" เดียวกัน — จัดอันดับ
ชุมชนทั้งหมด 85 แห่งพร้อมกัน (รายได้ + % การเติบโต) ดาวน์โหลดเป็น Excel

### รายละเอียดทางเทคนิคที่ควรรู้

- **ฟอนต์ไทยใน PDF**: jsPDF ไม่มีฟอนต์ไทยมาให้ในตัว ใช้ฟอนต์ Sarabun (จาก Google Fonts,
  ลิขสิทธิ์ SIL Open Font License 1.1 — ใช้/แก้ไข/ฝังในเอกสารที่สร้างได้อย่างอิสระ) ฝังไว้ใน
  `src/assets/sarabunFontBase64.js` ทดสอบเรนเดอร์จริงแล้วว่าภาษาไทยอ่านได้ถูกต้องสมบูรณ์

  **เคยลองใช้ Tahoma แต่เปลี่ยนมาเป็น Sarabun เพราะ:** Tahoma เป็นฟอนต์ลิขสิทธิ์ของ
  Microsoft การฝังฟอนต์เข้า PDF ต้องฝังไฟล์ฟอนต์เป็น base64 ลงในซอร์สโค้ดโดยตรง (ไม่ใช่แค่
  ใช้ฟอนต์ที่ติดตั้งอยู่ในเครื่องผู้ใช้) ซึ่ง EULA ของ Tahoma ห้ามคัดลอก/แปลงไฟล์/แจกจ่ายไป
  เครื่องอื่นไว้ชัดเจน (มีลิขสิทธิ์ Windows/Office ในเครื่องไม่ได้แปลว่ามีสิทธิ์ฝังไฟล์ฟอนต์ลง
  ซอร์สโค้ดที่แจกจ่ายต่อได้) Sarabun เป็นตัวเลือกที่เหมาะกว่าเดิมด้วย เพราะเป็นฟอนต์มาตรฐาน
  ราชการไทยตามมติคณะรัฐมนตรี ใช้ในเอกสารราชการได้ถูกต้องและไม่มีปัญหาลิขสิทธิ์เลย
- **ไลบรารีที่เพิ่ม**: `xlsx` (SheetJS) สำหรับสร้างไฟล์ Excel, `jspdf` สำหรับสร้าง PDF —
  `xlsx` มี CVE เก่า 2 รายการ (Prototype Pollution, ReDoS) แต่ทั้งสองเกิดเฉพาะตอน "อ่าน"
  ไฟล์ที่ถูกสร้างมาโจมตีโดยเฉพาะเท่านั้น เราใช้ไลบรารีนี้แค่ "เขียน/สร้าง" ไฟล์จากข้อมูลที่
  รู้ที่มาแน่นอน ไม่มีจุดไหนอ่านไฟล์ที่ผู้ใช้อัปโหลดเลย จึงไม่เข้าเงื่อนไขที่จะถูกโจมตีได้จริง
  — ยังเป็นเรื่องที่ควรรู้ไว้เผื่อมีคนสังเกตเห็นตอนรัน `npm audit`
- **ขนาดไฟล์ PDF** ประมาณ 2-3 MB ต่อไฟล์ (ฟอนต์ที่ฝังเข้าไปทั้งไฟล์ + กราฟที่วาดเป็นรูปภาพ)
  ปกติสำหรับการดาวน์โหลดครั้งเดียว ไม่กระทบความเร็วโหลดหน้าเว็บ เพราะ code ส่วน PDF จะโหลด
  เฉพาะตอนกดดาวน์โหลดจริง (dynamic import) ไม่ได้รวมอยู่ใน bundle หลักที่โหลดทุกครั้ง

## อัปเดตล่าสุด: แก้ตัวเลขรายได้สุทธิไม่ตรง + ตรรกะ "0 ต่อเนื่องนาน = ไม่ได้กรอกข้อมูล"

1. **ตัวเลขใน "สัดส่วนแหล่งรายได้" บวกกันแล้วไม่เท่ากับ "รายได้สุทธิ"** — ตรวจสอบแล้วว่า
   สูตรคำนวณถูกต้องมาตลอด (310,200 − 24,950 + 15,520 = 300,770 ตรงกับ KPI เป๊ะ) ปัญหาอยู่ที่
   การนำเสนอ: การ์ดเดิมโชว์ทั้ง 4 ตัวเลข (ขาย/ซื้อ/แบ่งปัน/ลดรายจ่าย) เป็นแท่งสีบวกเท่ากันหมด
   ทำให้เข้าใจผิดว่าบวกกันแล้วต้องได้รายได้สุทธิ ทั้งที่ "ซื้อ" ต้องหัก ไม่ใช่บวก และ
   "ลดรายจ่ายครัวเรือน" ไม่ได้อยู่ในสมการรายได้สุทธิเลย — ออกแบบใหม่ให้กราฟแท่งมีแค่ขาย+
   แบ่งปัน (2 ส่วนที่บวกจริง), ซื้อแยกเป็นบรรทัด "หักออก" ต่างหาก, ลดรายจ่ายครัวเรือนแยก
   ออกมาเป็นกล่องบอกชัดว่า "ไม่นับรวมในรายได้สุทธิ" และมีสูตรท้ายการ์ดให้ตรวจทานตรงกับ
   KPI ด้านบนได้เลย
2. **"ครบแต่ไม่มีรายได้" ควรเทียบเท่า "ไม่มีข้อมูล" ไหม** — ใช่ ถ้าเป็น 0 ทุกยอด (ขาย ซื้อ
   แบ่งปัน ลดรายจ่าย) ต่อเนื่องกันตั้งแต่ 4 เดือนขึ้นไป ตอนนี้ระบบจะตัดเดือนเหล่านั้นออกจาก
   การนับว่า "มีข้อมูล" โดยอัตโนมัติทั้งระบบ (แผงความครบถ้วน, KPI, กราฟแนวโน้ม, การวิเคราะห์
   เชิงลึก, การจัดอันดับเทียบภาค, รายสมาชิก) ไม่ใช่แค่จุดเดียว — เกณฑ์ 4 เดือนปรับได้ที่
   พารามิเตอร์ `minRunLength` ของฟังก์ชัน `findLikelyUnenteredMonths()` ใน
   `communityAggregations.js` ถ้าต้องการเปลี่ยนเกณฑ์

ไฟล์ `likely_unentered_month_runs.csv` ที่ส่งมาด้วยคือผลสแกนทั้ง 85 ชุมชนด้วยตรรกะใหม่นี้ —
แยกไว้แล้วว่า 83 ช่วงเป็น "เดือนอนาคตที่ยังไม่เกิดขึ้นจริง" (ไม่ต้องตรวจสอบ ระบบจะไม่นับว่า
มีข้อมูลให้เองโดยอัตโนมัติ ถูกต้องแล้ว) ส่วนอีก 16 ช่วงเป็นช่วงในอดีตที่จบไปแล้วจริง ๆ
(เช่น กุดขาคีม ปะกาฮะรัง ม่วงชุม ฯลฯ) ซึ่งควรตรวจสอบกับข้อมูลต้นทางว่าชุมชนนั้นหยุดส่งข้อมูล
จริงหรือเป็นปัญหาการกรอกข้อมูล

## อัปเดตล่าสุด: แก้ปัญหาแท็บ "ข้อมูลเชิงวิเคราะห์" 3 จุด

1. **บาร์ความครบถ้วนของข้อมูลไม่แสดงผล** — สาเหตุคือ `.completeness-bar-fill` เป็น
   `<span>` ซึ่งเป็น inline element ตามค่าเริ่มต้น การกำหนด `width` ผ่าน inline style
   จึงไม่มีผลใด ๆ (width ใช้ไม่ได้กับ inline element) ทำให้แท่งสีเขียวที่ควรยาวตาม %
   ความครบถ้วนไม่ปรากฏเลยไม่ว่าค่าจะเป็นเท่าไหร่ ก็เจอบั๊กเดียวกันที่แท่งกราฟมินิ
   (mini-bar) ในแท็บรายสมาชิกด้วย แก้โดยเพิ่ม `display: block` ให้ทั้งสองจุด
2. **ข้อมูลในแท็บวิเคราะห์เชิงลึก/เปรียบเทียบไม่เปลี่ยนตามตัวกรองที่เลือก** — เดิม
   ออกแบบให้ 2 แท็บนี้ใช้ "ปีงบล่าสุดที่ข้อมูลครบ 12 เดือน" เสมอ โดยไม่ขึ้นกับปีที่เลือก
   ในตัวกรองบนสุด (ตั้งใจป้องกันไม่ให้วิเคราะห์ข้อมูลที่ไม่ครบปี) แต่ทำให้สับสนเพราะ
   ป้ายปีในแท็บไม่ตรงกับตัวกรอง — เปลี่ยนให้ใช้ปีที่เลือกไว้จริงเสมอ ถ้าข้อมูลไม่ครบจะมี
   แถบเตือนสีส้มขึ้นอธิบาย (ไม่บล็อกการแสดงผลแล้ว)
3. **ไม่มีตัวเลือกปีปฏิทินเหมือนหน้าแรก** — เพิ่ม toggle ปีงบประมาณ/ปีปฏิทินในหน้า
   รายชุมชนแล้ว ทำงานเหมือนหน้าแรกทุกแท็บย่อย (ยกเว้นแท็บภาพรวม ซึ่งความครบถ้วนข้อมูล
   และกราฟ 4 ปีงบยังคงแสดงปีงบจริงเสมอ เพราะเป็นภาพรวมประวัติทั้งหมด ไม่ใช่ "ข้อมูลของ
   ช่วงที่เลือกดู")

ฟังก์ชันคำนวณใน `communityAggregations.js` เปลี่ยนจากรับ "fiscal year key" เป็นรับ
"{start, end}" ตรง ๆ แล้ว (ดูฟังก์ชัน `getPeriodRange()` ใน `fiscalYears.js`) เพื่อให้ใช้ได้
ทั้งสองโหมดด้วยโค้ดชุดเดียว

## ขึ้นปีงบประมาณใหม่ต้องทำอย่างไร

ฝั่ง backend (Apps Script + Sheets) ไม่ต้องทำอะไร — ทำงานแบบไม่ผูกกับปีงบอยู่แล้ว
(เก็บข้อมูลเป็นแถวต่อเดือนธรรมดา) ข้อมูลเดือนใหม่ที่กรอกผ่านฟอร์มจะเข้าระบบได้ปกติ

ฝั่ง React ต้องเพิ่ม 1 จุดเท่านั้น: เปิด `src/pages/fiscalYears.js` แล้วเพิ่ม key ปีงบใหม่ใน
`FISCAL_YEAR_RANGES`, `FISCAL_YEAR_ORDER`, `FISCAL_YEAR_DISPLAY_LABEL` (3 ค่าคงที่ในไฟล์
เดียวกัน) — ทุก dropdown ปีงบทั้งระบบ (หน้าแรก, หน้ารายชุมชน) ดึงตัวเลือกมาจากไฟล์นี้
ไฟล์เดียว ไม่ต้องไปแก้ที่อื่นอีก (เคยมีปัญหาว่า FilterBar.jsx กับ CommunityHeader.jsx
hardcode รายการปีงบของตัวเองแยกกันคนละชุด ซึ่งทำให้ label ของปีงบ 2565 ผิดไม่ตรงกับ
ช่วงวันที่จริงอยู่พักหนึ่ง — แก้รวมเป็นจุดเดียวแล้ว)

## ยังไม่ได้ทำ / ข้อจำกัดที่รู้อยู่แล้ว

- ไม่มีระบบบัญชีผู้ใช้แยกราย — ใช้รหัสผ่านร่วมตามที่ตกลงกันไว้ (ดู decision log ของโปรเจกต์)
- `monthly_summary` ไม่ถูกอัปเดตอัตโนมัติตอนอนุมัติข้อมูลใหม่ (`handleApproveSubmission` ใน
  `ApprovalApi.gs` อัปเดตแค่ `monthly_records`) — หน้าภาพรวม/รายชุมชนจะยังไม่เห็นข้อมูลที่อนุมัติ
  ใหม่จนกว่าจะมีการรีเฟรช `monthly_summary` ด้วยวิธีอื่น (เช่น รัน pipeline ใหม่ หรือเพิ่มฟังก์ชัน
  คำนวณสรุปใหม่ฝั่ง Apps Script) — เป็นช่องว่างของ backend ที่มีอยู่แล้ว ไม่ใช่บั๊กของหน้า React
- พิกัด lat/long ของชุมชนยังไม่มี (ใช้ตารางจังหวัดแทนแผนที่จริง)
